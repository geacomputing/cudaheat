\section{Implementation}


CUDAHeat is implemented as a Python package with a narrow public interface and separable numerical components. \code{core.py} orchestrates input preparation, device execution and result assembly; \code{climatology.py} and \code{detection.py} contain the numerical kernels; \code{result.py} defines sparse event accessors; and \code{enrichment.py} evaluates extensible event rules. The top-level \code{CUDAHeat} class provides \code{run()}, \code{climatology()}, \code{thresholds()}, \code{mask()}, \code{detect()} and \code{validate()} methods. The distinction between generic field production and event detection prevents allocation of full timestamp-aligned fields when only a compact event catalogue is needed.

The software uses CuPy for production GPU arrays but retains a NumPy reference path for numerical diagnostics. Device availability is required when constructing \code{CUDAHeat}, whereas importing the package does not itself require CuPy. This design permits workflows that inspect results, post-process catalogues or validate stored outputs on systems without a CUDA runtime.

\subsection{NetCDF and xarray Input Handling}

The I/O layer resolves the temporal coordinate, identifies spatial dimensions and preserves coordinate information needed to reconstruct the original grid. A source may be opened eagerly or through Dask-backed xarray reads. Lazy I/O constrains host-side read memory; it does not alter the complete-time requirement of the GPU calculation. Each spatial batch still contains every timestamp for its selected points, and data are converted to the explicit analysis precision before device execution.

\subsection{Point-Layout Optimization and Input Caching}

For a conventional gridded NetCDF file, the preprocessing layer can write a compact cache in which spatial dimensions have been stacked into point. The cache is separate from the raw archive and records source identity and layout metadata. It is therefore an optimization of access pattern rather than a replacement scientific data product. The option \code{input_optimization="auto"} uses an existing compatible point layout or prepares one; \code{"skip"} retains direct input handling, whereas \code{"require"} rejects an unoptimized grid.

Compact climatology and threshold cycles can likewise be stored in a Zarr cache for compatible optimized path inputs. The cache contains the small annual-cycle fields rather than a dense timestamp-aligned threshold field, preserving the memory advantage of the cyclic representation. Cache keys incorporate the baseline, percentile, smoothing choices, calendar mode and source metadata so that changes to the analytical definition invalidate reuse.

\subsection{GPU Batching and VRAM Management}

The executor transfers complete-time spatial batches to the selected CUDA device. When \code{batch_size="guess"}, an initial size is selected from a conservative fraction of free VRAM; an explicit positive batch size may also be supplied. A configurable safety reserve, 15\% by default, is retained from currently free memory. If a device out-of-memory exception occurs, the failed batch is released, its spatial width is reduced and the same spatial subset is retried. No time axis is partitioned during this recovery.

Although the API accepts selected device identifiers, the current implementation executes batches sequentially on the first selected device. Telemetry records host read, host preparation, transfer and GPU timings per batch, together with retry information and the active batch size. These diagnostics are operational metadata, not substitutes for scientific validation of the SST product or the event definition.

\subsection{Event and PostgreSQL Persistence}

Results are represented as xarray datasets so that event tables, point coordinates and metadata remain interoperable with the scientific Python ecosystem. The optional PostgreSQL layer is deliberately a simple, fast-accessible catalogue rather than a numerical archive. Large numerical arrays (including SST, the climatological cycle and threshold fields) remain in separately managed Zarr stores, where chunked reads and storage-local spatial batching are more appropriate than relational row storage. PostgreSQL retains the small, query-oriented objects needed to find, filter and relate analyses: run provenance, spatial identities, sparse events and rule outputs.

The catalogue is connected to the numerical stores through content-derived identifiers. A run records the source checksum and climatology hash; the spatial grid is represented by a grid fingerprint; and every enrichment output records the SHA-256 hash of the YAML rule that produced it. These hashes provide traceability across the catalogue and the external Zarr data: an event query can be traced to its source SST, reference cycles, detection configuration and executable enrichment specification without copying the numerical arrays into the database. 

\subsection{Database architecture}
The relational schema comprises four tables: \code{runs}, \code{points}, \code{events} and \code{event_enrichments}.

\noindent\textbf{Runs.} Each row in \code{runs} is one immutable detection configuration, identified by a UUID and a 64-character \code{run_fingerprint}. The row stores the paths and hashes that identify the external numerical stores, together with the variable, baseline, percentile, smoothing and calendar choices, temporal continuity parameters, analysis precision, device selection, batching metadata, CUDAHeat version, Git commit and complete JSON metadata. A unique partial index on \code{run_fingerprint} prevents an equivalent configuration from being silently stored twice. The row therefore provides the provenance required to distinguish a new scientific analysis from a repeated persistence request.

\noindent\textbf{Points.} The \code{points} table represents the spatial grid independently of any particular run. Its natural key is \code{(grid_fingerprint, grid_point_index)}, where the grid fingerprint is a SHA-256 digest of point indices, geographic coordinates and available original-grid indices. Latitude, longitude, original latitude and longitude indices, and the original flat index are retained when available. This separation allows many runs that use the same grid to reference one stable spatial identity rather than duplicating coordinates for every run or event.

\noindent\textbf{Events.} The \code{events} table is the sparse fact table. Each row references one \code{run_id} and one \code{point_id}, and records the CUDAHeat event index, half-open start and stop indices, start and end timestamps and duration in hours. The pair \code{(run_id, cudaheat_event_index)} is unique, while the \code{(run_id, point_id, start_time)} index supports point- and time-constrained catalogue queries. An event is therefore identified by its analytical context and spatial location, not only by a timestamp interval that might have a different meaning under another baseline or gap rule.

\noindent\textbf{Enrichment outputs.} The optional \code{event_enrichments} table is a child of \code{events}. It stores the rule identifier, semantic version, source hash, JSONB result object and application time. The uniqueness constraint \code{(event_id, rule_id, rule_version)} prevents duplicate application of the same rule version to an event, and the persistence layer rejects a changed source hash for an already stored rule identifier and version. Retroactive enrichment reconstructs the sparse catalogue from \code{events} and \code{points}; SST, climatology and threshold arrays are read from their hash-linked Zarr stores, preserving the database as a catalogue and provenance layer rather than a second numerical archive.

The separation of these tables is deliberate. Run-level parameters would be highly redundant if repeated for every event, and spatial coordinates would be repeated for every event and every analysis if they were not normalized. Conversely, storing events as a dense time--space cube would defeat the sparse representation used by the detector. Foreign keys preserve referential integrity; deleting a run cascades to its events and enrichment outputs, whereas reusable point identities are retained. Persistence is executed in one database transaction: the schema is created if needed, the run is checked for duplication, grid points are upserted, events are inserted and enrichment outputs are attached.
